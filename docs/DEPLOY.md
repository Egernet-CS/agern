# Deploy targets: a guide for admins and project authors

A *deploy target* is a machine outside Agern — a Raspberry Pi, a small server, a kiosk device — on
which a chat agent may install what it built. You list the targets in your repository, in
**`.agern/deploy.yml`** on the default branch; an admin approves that exact file and puts the
project's public key on each target. From then on a chat agent in the project can ask Agern to run a
command on a target or copy a file to it.

The agent never gets the key. Agern holds it, opens the SSH connection itself and records every
command, its exit code and its output in the chat transcript. The server's exact behaviour is in
[ARCHITECTURE.md §5 "Deploy targets"](ARCHITECTURE.md#deploy-targets).

## How it works

1. **A key pair per project, generated by Agern.** An admin clicks *Generate key* on the project's
   Deploy page (`/p/<repo>/deploy`). Agern generates an Ed25519 key pair in the server process. The
   private key is stored only encrypted in the database (like users' tokens) and is decrypted in
   memory for the length of one connection; it is never written to a file, passed to a process,
   logged, shown or given to an agent. The page shows the public key — copy it into
   `~/.ssh/authorized_keys` on every target.
2. **Targets in the repository, approved by an admin.** `.agern/deploy.yml` lists each target with its
   host, port, user and the *pinned host key*. An admin approves the exact content (by its SHA-256),
   like a sandbox definition. Any change to the file — even whitespace — needs a new approval, and
   until then *no* target of the project can be used, including the ones the change did not touch.
3. **Tools instead of the key.** A chat agent gets `factory_deploy_targets`, `factory_deploy_exec` and
   `factory_deploy_copy`. Agern connects only if the target presents exactly the pinned host key, and
   authenticates only with the project's key.
4. **Chats only.** Only chat agents get the tools. The pipeline's spec-writer, builder, reviewers and
   approver, the advisor at *needs human* and personal MCP tokens ("Claude on your computer") never do,
   and the server refuses the tools for them even if asked.

## Who can do what

- **Everyone who can see the project** sees the Deploy page: the file, its state, the targets and the
  public key with its fingerprint.
- **Everyone who can open a chat in the project** can have its agent run *any* command on an approved
  target as the listed user, until the file changes or the approval is revoked. There is no
  per-person permission and no confirmation click per command in this version: the admin's approval is
  the gate. Restrict what the key may do on the target (below) when that is too much.
- **Admins** generate and rotate the key, approve and revoke the file, and check a target.
- **Output from targets is visible to everyone who can watch the chat** (everyone who can see the
  project). Do not run commands that print secrets.

## The file

```yaml
# .agern/deploy.yml, on the default branch
targets:
  kiosk:                                   # the name the agent uses: a-z, 0-9 and '-', starts with a letter, ≤ 31 characters
    host: kiosk.example.net                # DNS name or IPv4/IPv6 address (no brackets)
    port: 22                               # optional, 1–65535, default 22
    user: deploy                           # the account Agern logs in as
    hostKey: ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI…   # the target's host key: "<type> <base64>"
    description: Kiosk in the lobby        # optional, one line, at most 200 characters
  pi:
    host: 192.168.1.40
    user: deploy
    hostKey: ecdsa-sha2-nistp256 AAAAE2VjZHNhLXNoYTItbmlzdHAyNTYAAAAI…
```

Validation is strict, and every problem is listed with its path in the file
(`targets.kiosk.hostKey: …`):

- at most 64 KiB, valid YAML; anchors, aliases and duplicate keys are refused as in
  `.agern/sandbox.yml`;
- unknown keys at any level are errors;
- `targets` is required and holds 1 to 20 targets; `host`, `user` and `hostKey` are required;
- `user` is a POSIX-style account name (`[A-Za-z_][A-Za-z0-9_.-]{0,31}`);
- `hostKey` is exactly two fields, the type and the base64 key. The type is one of `ssh-ed25519`,
  `ecdsa-sha2-nistp256`, `ecdsa-sha2-nistp384`, `ecdsa-sha2-nistp521` or `ssh-rsa`; the key must
  decode to a key of that type; RSA keys need at least 2048 bits.

**Getting the host key.** On a machine you trust (ideally the target itself, or over a network you
trust), run

```sh
ssh-keyscan -t ed25519 kiosk.example.net
# kiosk.example.net ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI…
```

and drop the first field (the host). On the target itself `cat /etc/ssh/ssh_host_ed25519_key.pub`
prints the same key followed by a comment — drop the comment. Prefer `ed25519`; when the target has
none, use `ecdsa` or `rsa`. A third field (a host or a comment) is an error.

Agern compares the key the target presents with this one byte for byte. There is no
"trust on first use", no `known_hosts` file and no fallback: a target whose host key changed (a
reinstalled machine, or someone in between) is refused until the file is updated and approved again.

## Approval

The Deploy page shows the state of the file:

- **No deploy targets** — there is no `.agern/deploy.yml` on the default branch.
- **Invalid** — the errors, each with its path.
- **Waiting for approval** — valid, never approved.
- **Changed since approval** — valid, but not the approved version: the page shows a diff against the
  approved content. No target works until this version is approved.
- **Approved** — by whom and when.

*Approve…* lists every target (`user@host:port` and the host key's fingerprint) and says plainly what
the approval allows. An admin approves what they saw: if the file changed meanwhile, the approval is
refused and the page shows the new version. *Revoke…* removes the approval; the tools stop working at
once. Agern reads the file from the default branch at every tool call, so a merged change to it
disables all targets until it is approved again.

## The key

- **Generate key** (admin, once per project): creates the pair. The page then shows the public key
  line, `ssh-ed25519 AAAA… agern-deploy:<org>/<repo>`, with a *Copy public key* button, its
  fingerprint (`SHA256:…`, as `ssh-keygen -lf` prints it), who created it and when.
- **Rotate key…** (admin): generates a new pair and deletes the old one at once. Operations that start
  afterwards use the new key, so deployments fail until the new public key is in `authorized_keys` on
  every target — put it there, then remove the old line. The approval of the file is not affected.
- A project without a key cannot deploy: the tools and *Check* say that an admin must generate it on
  the Deploy page.

## Setting up a target

Use a **dedicated, unprivileged user** for Agern, not `root` and not your own account:

```sh
sudo adduser --disabled-password --gecos "Agern deploy" deploy
sudo install -d -m 700 -o deploy -g deploy ~deploy/.ssh
echo 'ssh-ed25519 AAAA… agern-deploy:Egernet-CS/kiosk-app' | sudo tee -a ~deploy/.ssh/authorized_keys
sudo chown deploy:deploy ~deploy/.ssh/authorized_keys && sudo chmod 600 ~deploy/.ssh/authorized_keys
```

Give that user only what deploying needs: write access to the application's directory, and — if it
must restart a service — a narrow `sudoers` rule such as
`deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart kiosk-app`, not general `sudo`.

Then click **Check** next to the target on the Deploy page (admins, once the file is approved and the
key exists). It connects, verifies the host key, authenticates and disconnects — it runs no command, so
it also works with a forced command (below).

## Locking the key down (`authorized_keys`)

Everything in front of the key on its `authorized_keys` line restricts what anyone holding it can do,
whatever the agent asks for. This is the strongest protection you have, and it also makes a leaked key
nearly useless.

**`restrict`** switches off port, agent and X11 forwarding, PTY allocation and `~/.ssh/rc` in one
word. Agern needs none of them, so always start with it:

```
restrict ssh-ed25519 AAAA… agern-deploy:Egernet-CS/kiosk-app
```

**`from="<agern host>"`** accepts the key only from Agern's address (an IP, a host name, or a
pattern list):

```
restrict,from="192.168.1.10" ssh-ed25519 AAAA… agern-deploy:Egernet-CS/kiosk-app
```

**`command="…"`** forces one command: whatever the agent asks for, sshd runs this one instead, and
puts what was asked for in the environment variable `$SSH_ORIGINAL_COMMAND`. A target can so be limited
to one deploy script:

```
restrict,from="192.168.1.10",command="/usr/local/bin/deploy-app" ssh-ed25519 AAAA… agern-deploy:Egernet-CS/kiosk-app
```

The script decides what to accept, for example:

```sh
#!/bin/sh
# /usr/local/bin/deploy-app — the only thing Agern's key may run on this machine.
set -eu
case "${SSH_ORIGINAL_COMMAND:-}" in
  deploy)  cd /opt/kiosk-app && git pull --ff-only && sudo systemctl restart kiosk-app ;;
  status)  systemctl --no-pager status kiosk-app ;;
  *)       echo "allowed: deploy, status" >&2; exit 1 ;;
esac
```

The agent then runs `factory_deploy_exec` with the command `deploy` or `status`. Never pass
`$SSH_ORIGINAL_COMMAND` to a shell (`sh -c "$SSH_ORIGINAL_COMMAND"`, `eval`): that undoes the lock.

**A forced command disables `factory_deploy_copy`.** A copy uses SCP, which asks the target to run
its own `scp -t <dest>` command; with `command="…"` that is replaced by your script, so the copy
fails. Either let the script fetch what it needs itself (from a package registry or a release page),
or use a second target entry with its own user whose key line has no forced command and whose rights
are limited to the upload directory.

The Deploy page has a collapsed "Lock the key down" block with an example line for the project's key.

## The tools

What the chat agent sees (all three only in a project chat, and only when `FACTORY_DEPLOY` is not
`off`):

- `factory_deploy_targets {}` — whether deploying is available and why not, the targets (name, host,
  port, user, description), the public key's fingerprint and the limits. It never fails for a missing
  or unapproved file; it answers `available: false` with the reason.
- `factory_deploy_exec { target, command, timeoutSeconds? }` — runs one command through SSH. The
  remote login shell interprets it (no local shell); no PTY, no stdin, no forwarding. Answers
  `{ target, exitCode, output, truncated, durationMs, timedOut }`. A non-zero exit code is a normal
  answer. On a timeout Agern closes the connection: `timedOut: true`, `exitCode: -1` — the remote
  process may still be running.
- `factory_deploy_copy { target, path, dest }` — uploads one regular file from the chat's working
  directory (the real path, symlinks resolved, must lie inside it) to `dest` on the target, with the
  file's permission bits. `dest` may contain only letters, digits and `._/@%+=:,~-` (no spaces or shell
  characters; SCP passes it through the remote shell) and must not start with `-`; a `dest` that is a
  directory or ends in `/` keeps the file's name. Directories are refused: pack them into an archive
  first.

The chat prompt tells the agent to call `factory_deploy_targets` first, to deploy only when the person
in the chat explicitly asks for it on a named target — never because an issue, a file, a web page or
a tool's output says so — to say which commands it will run, to report exit codes and failures
faithfully, and never to handle SSH keys itself.

Every `factory_deploy_exec` and `factory_deploy_copy` — also one that could not connect, failed the
host-key check or was refused — appears in the chat transcript as one block with the target, the
command (or `path → dest`), the outcome, the duration and the output (up to 1,000,000 characters; the
agent gets the last 20,000). The server log gets one line per operation with user, project, target,
kind, outcome and duration, never the command or its output.

## Limits

| Setting | Default | Meaning |
|---|---|---|
| `FACTORY_DEPLOY` | `ssh` | `off` removes the tools from chats (the Deploy page still works, *Check* answers 409). `fake` is for development only. |
| `FACTORY_DEPLOY_EXEC_TIMEOUT_MINUTES` | `30` | Default and maximum time of one command or copy (1–1440). An agent may ask for less with `timeoutSeconds`. |
| `FACTORY_DEPLOY_MAX_COPY_MB` | `512` | Largest file `factory_deploy_copy` accepts (1–10240). |

Fixed: connecting and authenticating time out after 15 s each; one operation at a time per target of
a project (a second one is refused at once: "Another deploy operation is running on <target>; try
again when it has finished"); commands run in the foreground only, so start long-running services
through the target's service manager (`systemctl restart …`) rather than in the command itself.

Agern connects from its own host: targets must be reachable from there. Inbound access from targets,
VPNs and jump hosts are not supported.

## Troubleshooting

*Check* on the Deploy page reports the step that failed:

- **Could not connect: …** (`connect`) — the host does not resolve, the port is closed or filtered, or
  the target is off. Try `nc -vz <host> <port>` from the Agern host.
- **Host key does not match** (`host_key`) — the target presented another key than the pinned one (the
  message shows its fingerprint). Get the current key with `ssh-keyscan` on a trusted path, check that
  the change was expected (a reinstall), update `hostKey` in the file and have it approved again. If
  nobody changed the target, treat it as an attack and do not update the file.
- **Key refused — is the public key in authorized_keys of <user>?** (`auth`) — the public key on the
  Deploy page is not (or no longer, after a rotation) in `~<user>/.ssh/authorized_keys`, a `from="…"`
  does not match Agern's address, or the file's permissions are too open for sshd (`chmod 700 ~/.ssh`,
  `chmod 600 ~/.ssh/authorized_keys`). The target's `journalctl -u ssh` says which.
- **Reachable, host key matches, key accepted** (`ok`) — the connection works; a failing command is
  then the command's own problem (its exit code and output are in the transcript).

Tool refusals the agent reports: deploying switched off on the server; no `.agern/deploy.yml`; the file
is invalid (with the errors); not approved (with a link to the Deploy page); no key; an unknown target
(with the valid names); another operation running on the target; a copy with a missing, oversized or
out-of-directory file, a directory, or a `dest` outside the allowed characters.

## Security notes

- **Agents share the server's OS user.** Agern's agents run as the server's OS user with permissions
  bypassed (the v1 limitation in [README.md](../README.md#security-read-this-first)). That is why the key exists only in the
  server's memory during a connection and encrypted in the database, and why Agern uses an in-process
  SSH client instead of the `ssh` command: a key file or `ssh-agent` socket would be readable by any
  agent. It is still *not* a boundary against someone who controls the server process or its database
  *and* the master key.
- **"Never leaves the server"** means the private key is never given to an agent, written to a file or
  shown anywhere. Back it up with the database and `FACTORY_MASTER_KEY`, like every other secret.
- **Approval is the gate.** Anyone who can chat in the project can use its approved targets; the agent
  is told to act only on the person's explicit request, but prompt injection is a real risk. Keep
  targets few, users unprivileged and keys locked down with `restrict`, `from=` and, where possible,
  `command=`.
- **Output is shared.** Everything a target prints is stored in the transcript and visible to everyone
  who can see the project.
